# Project Eye

The whole project from above, so a change can be made knowing what it touches.
Kept short on purpose: an encyclopaedia nobody reads is the same as no map.

Derived facts in this file come from `.project-eye/graph.yaml`, which is
generated by `python scripts/project_eye.py` from the imports that actually
exist. When the code and the graph disagree, `tests/test_architecture_rules.py`
fails. Rerun the scanner rather than editing the graph.

## 1. What this project is

A person demonstrates one browser task once — sign in, open a report, set its
filters, run the query, export the file. SmartOps watches, and turns that
demonstration into an automation it can repeat every morning without them.

The value is not the clicking. It is the proof: a run has only succeeded when a
file arrived, its real type was read from its bytes rather than its name, its
contents passed the configured checks, and the outcome is in the run history. A
click that landed proves nothing.

One business flow, deliberately. Underneath it, many ways to survive a screen —
because a corporate portal defeats any single one of them.

## 3. What actually runs

| Runtime | Started by | Does |
| --- | --- | --- |
| Web app | `START.cmd` → `smartops serve` → `api/app.py` | The interface a person uses, and the API |
| Worker | started by `serve`, or `smartops work` | Executes queued runs |
| Scheduler | same | Starts runs when they are due |
| Recorder | one thread per recording, inside the web app | Drives a headed Chrome and watches |
| Replay | inside a run, in the worker | Drives Chrome deterministically |
| Credential window | `credential_prompt` | A separate process, so a password never crosses the app |
| Chrome extension | loaded in the browser | A second, structural view of one shared tab |

## 4. Which way dependencies are allowed to point

```text
composition  ─── may depend on everything (that is its whole job)
     │
     ▼
web ──► recording ──► browser ──► contract ──► foundation
     │        │           │           ▲            │
     └────────┴───────────┴───────────┘            ▼
                                              persistence
```

The rules are written in `.project-eye/rules.yaml` and enforced by
`tests/test_architecture_rules.py`. The two that matter most:

* **The browser adapter must not know who produced the plan it runs.** It once
  loaded the element repository itself, which made the executor depend on the
  recorder. The graph caught it; the loading moved to the workflow step that
  already knew about both.
* **The web layer must not touch the database.** It asks a manager, which owns
  the decision and the transaction.

## 6. Who owns what state

| State | Authority | Everyone else |
| --- | --- | --- |
| A recording's steps | `RecordingManager` (SQLite) | `steps.jsonl` is a mirror, rewritten on undo |
| How a control is found | `ElementRepository` | A step's own locators are the fallback |
| What a step observed | `Timeline` (sidecar) | Never the step contract |
| Whether a frame is real | `PageVision` | `quality.jsonl` records the verdict |
| The signed-in session | `sessions.py`, one file per system | Recorder and replay both read it |
| Which tab is which | `worker._page_names` / `ReplaySession._page_names` | Names outlive the tabs |
| Run outcome | `RunRepository` | The interface reads, never writes |
| The Chrome profile | the owner file in the profile | One process at a time, enforced |

## 8. Red zones — known, recorded, not hidden

Found by the scanner. None is being quietly fixed; each is written down because
the contract's rule is that a map must never be redrawn to make a problem
disappear.

1. **`foundation ↔ persistence`.** `events/log` imports
   `storage/repositories` while `storage/repositories` imports `core/clock`.
   The event log is a foundation service that reaches down into storage.
   *Effect today:* none observed; both are stable and well covered.
   *Right fix:* the event log should take a repository interface, not import
   the concrete one. Not done: it touches the event system, which every domain
   publishes to, and it is not blocking anything.

2. **`contract ↔ foundation`.** `domain/models` imports `core/clock` while
   `events/*` imports `domain/*`. Small and stable, but it means the shared
   vocabulary is not a leaf.

3. **`browser ↔ shared`.** `sessions` imports `adapters/browser/session` to
   capture a login, while the browser adapter reads `config` and
   `credentials`. Sign-in genuinely spans both; the honest name for
   `sessions` is part of the auth domain, which does not exist yet.

4. **`operations` holds 24 modules with no clearer owner.** `checks`,
   `journey`, `login`, `recovery`, `chrome_bridge`, `operator_memory` and
   others. Not a domain — a bucket. Every one of them belongs to *something*;
   naming those owners is the next structural piece of work, and per the
   contract it comes after mapping, not instead of it.

5. **No end-to-end journey test on a real corporate portal.** Every journey in
   §5 is proved against local fixtures. The single largest gap in the project,
   and the only one that cannot be closed from here.

## 9. Where the risk concentrates

Roughly change-frequency × how much depends on it × how much is uncertain:

1. `recordings/worker.py` — changed almost every session, 5,658 lines in its
   domain, and the only place a human demonstration is observed.
2. `adapters/browser/replay.py` — every run goes through it, and a wrong
   change here acts on a real system rather than failing a test.
3. `recordings/converter.py` — decides what counts as proof; a mistake makes
   runs pass that should not.
4. `domain/enums.py` — small, but 24 modules deep.
